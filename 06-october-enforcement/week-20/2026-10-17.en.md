## ⏮ Previously on The Journey

Day 133: the fix never reached its consumer. Day 134: the guard was made of the same substance as what it guarded.

Day 135: nobody ever measured the judge's accuracy.

Today is different. **The instrument searches for evidence on the wrong carrier, and so it is blind to its own proof.** The proof exists and sits nearby, just somewhere else: in git history, in the mailbox, in someone else's repository, in CPU load.

🤖 **Mike:** On 135 we asked how often the judge is wrong. Today shows why it is wrong the same way every time: it opens the wrong drawer and honestly reports that the drawer is empty.

## 🎬 Cold-open

The lighthouse, the night of October 15. Before a full backup, the vault backup guard counts what changed.

To delete: 482 files. Without a recoverable copy: 139. Next to them: 57,490 additions.

The guard's threshold is 50. Four hundred eighty two is more than fifty, the backup is blocked.

The night of the 16th: the same. The night of the 17th: the same.

Three nights in a row the vault lives without a full backup, because the guard is afraid of losing files that never went anywhere.

🤖 **Mike:** A security guard stops the truck at the gate because boxes are missing from the inventory. The boxes are in the next hangar, and the key to it is in his pocket. He just does not count that hangar as part of the warehouse.

## 📌 TLDR

**Main.** The lighthouse backup guard blocked the full backup three nights running (October 15, 16, 17): 482 files to delete, 139 "without a recoverable copy". Every blob was in HEAD. `_recoverable()` does not count git history as a copy, and the threshold is binary: 482 is above 50, so stop.

The same root was diagnosed on July 23 and never fixed.

**Same class nearby.** xAI applications: 12 confirmations in the mailbox against 6 rows in the database, and a preflight with a hardcoded path answered "allowed" for any url. The force-push rule lived only in instruction text with no mechanical door, and review anchors in other people's PRs got wiped. The MCP reducer judged a process by its age, not by its work.

The PR watcher looked only at our 68 repos and missed 14 debts in foreign ones. The DR runner complained "the package does not arrive", and the broken part was the instrument.

## 🏆 Main story

### A guard that did not believe in git

#### Three nights

The guard's numbers are identical across three nights: 482 to delete, 139 without a copy, 57,490 additions. The decision is identical too: stop.

A raw `git status` on the same files gives 723. That is not a contradiction, it is another instrument with another definition of "changed". Two numbers about one tree, and neither says how much data is actually at risk.

🧑 **Tony:** So how many files could we really have lost?

🤖 **Mike:** To answer that you ask git, not the disk. Git answered: all blobs present, in the latest commit.

#### Where the guard looked for a copy

`_recoverable()` asks one question: does the file being deleted have a copy it can be restored from. It looks at backups and neighbouring folders.

It does not count git history as a copy.

For the vault, git history is the main copy. Each of the 139 "unrecoverable" files sat whole in HEAD.

🤖 **Mike:** The guard asked "where is the copy?" and looked only where copies usually are not. Where the copy always was, it did not look, by definition.

#### A threshold that does not measure

The second half of the root: the threshold is binary. Fifty files or fewer, the backup runs. More than fifty, it stops.

The threshold does not ask what share of deletions is recoverable, how many additions sit next to them, or what git said. Four hundred eighty two recoverable files weigh the same as four hundred eighty two real deletions.

🧑 **Tony:** The threshold was supposed to be a measure and became a wall?

🤖 **Mike:** Yes. A counter turned into a barrier. The barrier does not know what the truck carries.

#### July 23

The worst part was in the diagnosis history. The same root, `_recoverable()` blind to git, had been taken apart on July 23.

The diagnosis was written down. The fix was not made.

For almost three months the guard lived with a known blindness, and three nights in a row it cost the vault its full backup.

🤖 **Mike:** A diagnosis without a fix is a message in a bottle. Someone found it, read it, and threw it back into the sea.

#### Links without a commit

Two more gaps opened in the same zone, both about where the result lives.

On October 16 the link janitor applied 17 links to vault notes. Applied, not committed.

For twenty four hours the changes lived only on disk, and for any instrument reading git they did not exist. The result was real, the carrier was wrong.

Second gap: the applicator rejects HIGH-confidence links based on the parent folder. If two notes sit in different branches of the tree, a link between them is suspect even when the meaning matches.

First pass: 22 of 39 pairs rejected. Then 14, then 12, then 7.

🧑 **Tony:** It judged a link by the note's address, not its meaning?

🤖 **Mike:** By the postcode, not the letter. Each pass lets a little more through, but the criterion stays the same.

### Twelve confirmations and six rows

xAI applications, October 4 to 7. The mailbox holds 12 confirmations of receipt. `jobs.db` holds 6 rows with `status=new` for the same days.

The database saw half. The mailbox saw everything.

Meanwhile the panel said "323 applications over the cap". A recount gave 219. The instrument's tests were green: `Ran 22 OK`.

🤖 **Mike:** Twenty two tests confirmed the instrument runs. None of them asked whether it was looking at the right carrier.

Three roots, all about the carrier.

First: the preflight had a hardcoded `E:\` path. Where that path did not hold the data, the check found nothing and answered "allowed" for any url. Absence of evidence read as permission.

Second: there was no per-employer cap at all. A global counter existed, but the question "how many have we already sent here" was never asked.

Third: `build_cache` overwrites entries with the same url. Two applications to one posting collapsed into one row, and the instrument went blind to its own duplicates.

🧑 **Tony:** So the database itself erased the evidence that we overdid it?

🤖 **Mike:** It kept the last record per url. The witnesses of the repeat were destroyed at write time.

Fix: `run_slice.py` cuts applications into slices with a per-employer cap check, a cap test goes red on violation, and the probe `_probe_run_slice_gates.py` checks the gates against live data.

### A rule with no door

`git push --force-with-lease` sounds safe. It is safe for your own branch.

In someone else's PR a bare force-push wipes the expected review anchors: the reviewer's comments hang on commits that no longer exist. The maintainer opens the PR and finds his notes detached from the code.

The family had four such cases. One PR was closed as `CHANGES_REQUESTED`.

The rule "do not rewrite history under a reviewer in a foreign PR" existed. It lived in the instruction text of the `/pr-reply` skill.

🤖 **Mike:** The rule was written in the book the agent opens when replying to review. When it pushes, the book is closed. The carrier of the rule and the place of the action never met.

There was no mechanical door. The hook `force_push_review_gate.py` now sits in front of the push itself and stops a bare force-push into a branch awaiting review. It comes with a test.

Rollout reached 4 of 8 nodes. The other four lag, and that is recorded.

#### The dot that got eaten

On the way, a side root turned up in `deploy_register.py`. Paths were cleaned with `lstrip("./")`.

`lstrip` removes not a prefix but any characters from the set at the start of the string. The path `.claude/...` became `claude/...`.

The rollout registry wrote the file down where it did not live, then failed to find it where it looked.

🧑 **Tony:** One dot, and the instrument searches a folder that does not exist?

🤖 **Mike:** Yes. The address of the evidence was corrupted at write time, so the evidence "vanished". Fixed with `_suffix_hit`: match on the path tail, not on the trimmed string.

### Old is not idle

The idle MCP reducer is meant to shut down servers that do nothing. It judged by age: started long ago, so idle.

Age is not the carrier of idleness. A server started a week ago may work every minute.

Shadow since October 14, harvest set for the 21st. In that time, 22 human turns, `fails=0`. A live dry-run produced 0 candidates.

🤖 **Mike:** Zero candidates from an age judge does not mean "all is working". It means the judge was looking at the clock, not at the work.

The reducer was rebuilt to judge by CPU delta between two samples. The routine will exist only after the shadow harvest.

The author named the weak link himself. Right now the proof is carried by a unit test and a mutant, not by a live run. That is written next to the fix, not hidden.

### A watcher that looked only at our own repos

`contrib-watch` makes sure incoming engineer touches do not go unanswered. It watches our 68 repositories.

The same day `pr_watch` showed 14 PRs in "ball in our court" state in foreign repositories. People wait for our answers there, and the watcher never looks.

One debt is 20 days old. `gh pr view` no longer resolves it.

🧑 **Tony:** The watcher said "all answered" while people waited twenty days?

🤖 **Mike:** The watcher told the truth about our repos. The debts lived in other people's. Wrong drawer.

The family class counter said "first time". It was the fourth.

The fix already has an owner, the `/pr-reply` skill. No new card was opened, the debt went to it.

### A queue where humans are not first

The lost sessions queue should lift abandoned live dialogues with Anton to the top. `list --top 200` returned 98 rows.

Live dialogues sat at positions 4, 5, 9-18 and 82. Other sessions held the top.

`retro_lost_scan.py` has not changed since October 3. The sorting test arrived, the fix did not.

🤖 **Mike:** The test checked the right order while the code kept sorting the old way. Evidence of correct behaviour lived in the test file, not in the executable one.

Locally ported: human-first sorting and `_distilled_elsewhere()`, so a session whose meaning was already distilled elsewhere does not take a slot.

### "The package does not arrive"

The DR runner on one node complained that the prompt package does not arrive. It looked like a bus failure.

The instrument was what broke. It counted 222 sync collisions and read them as non-delivery.

The hub had fixed that instrument back on September 4. On this node the fix was not in place.

🧑 **Tony:** All this time we thought the package was lost?

🤖 **Mike:** The package arrived. The scale at the post office was broken and read zero.

Three empty runner slots were filled. Along the way it turned out that 3 of 6 nodes have a different memory path, so an instrument reading memory from one path looked into an empty folder on half the fleet.

### What follows

The backup guard looked for the copy on disk, and it was in git. The application preflight looked for data on a drive that is not there. The links lived on disk and never reached a commit.

The force-push rule lived in an instruction while the action happened in a command. The reducer measured age instead of work. The PR watcher looked in our repos while the debts were in foreign ones.

Every time the proof existed. Every time the instrument opened the wrong drawer.

The difference from the neighbouring chapters. 133 was a fix that did not arrive. 134 a guard of the same substance.

135 a judge without an exam.

136 is a judge with perfect eyesight looking into the other room.

Rule of the day: **before an instrument says "no", it names the carrier it searched and every carrier where that fact could live.**
