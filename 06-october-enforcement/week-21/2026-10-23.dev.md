# Day 142 - 2026-10-23: a true reading expires between the check and the irreversible click

Dev-log form.

Defect: value `V` is read at time `t0` from copy `C`; irreversible action `A` fires at `t1`. `C` lags ledger `L`, and no claim on `A`'s slot is held over `[t0, t1]`. `V` was true at `t0` and false at `t1`.

Variants: mirror table instead of registry; per-session disclosure under parallel writers; free outbound slot with two executors; stale ask counted as free; fix deployed to a tree that is not the one that runs.

Position on the line. 138: rule in words loses to a door. 139: empty input reads as green.

140: two correct guards sum to failure, sum unowned. 141: green receipt over a dead output. 142: true reading expires before the click.

---

## 0. Contract

Before an irreversible action: read the count from the ledger, not a mirror; hold a claim on the slot; re-read live state at the last moment before the act.

A consent token must outlive the polling period of its reader. A fix is deployed only when the running tree carries it.

## 1. Application cap from a lagging mirror

Seed: "1 submitted, 3 left" (local DB). Fleet registry: 6. Gate union count: 9.

Limit: 4 per 180 days.

Cause: gate counted only a mirror table that lags the fleet ledger.

Solution: neighbour session had already fixed the gate (red proof FAIL E10/E10b on old code). Gate computed capped until 2027-04-17. Submitted 0.

Own error: window-open date counted by eye twice, wrong twice; panel caught it.

Open: rollout to other nodes unverified; seed generator may keep stale counts; Syncthing stall blinds the gate again.

Pattern: the gate counts the ledger, and computes dates itself.

## 2. Parallel submissions, stale disclosure

Five parallel sessions submitted overlapping applications, ~11:35-12:39 UTC. Each session's "other applications" disclosure was stale within an hour.

Solution: shared submissions ledger (10 rows). Not atomic, no door before the click.

Side finding: status comes from the confirmation email, not the card field (one card wrongly closed as done).

Pattern: a disclosure written at turn start is a snapshot; with parallel writers it needs a shared, claimed ledger.

## 3. Vendor cap unknown before the wave

Two roles at one vendor rejected by a banner "limiting applications within the last 90 days"; recorded as validation error (banner needle too narrow). Submitted 0.

Solution: needle fixed in 2 files; `VENDOR_CAPS=(1,90)`; regression red on old code. Class vendor-cap-unknown-before-wave: 3/3.

Open: cap per company or per domain (unknown).

## 4. Duplicate after-call order

Two sessions executed the same after-call order. The other session (Codex) had already sent intros and follow-up.

Stopped only by re-reading the live thread before Send. Class parallel-sessions-same-outward-slot-no-claim: 2/3 (first case 10-12).

Pattern: outbound slot needs a claim; last-second re-read is the backstop, not the mechanism.

## 5. Thread-clean: 17 asks from a stale slot

17 asks issued instead of 5 (12 revoked). Cause: a stale ask counted as a free slot. A bare "+" in the approval chat expires in 15 min; the ear ticks every 2 h.

CRM deletion: 1655 messages in 4 batches (306+38+593+718), verified by re-read. 8 messages silently kept by Telegram, caught by `delete_verified`. Tally: 2499 deleted, 9 not; intents 365 = results 365.

Batch 04 hung 3 times (8, 25, 23 min). Cause: second connection on the same session key as the always-on Telegram MCP; not FloodWait.

Pattern: consent TTL >= reader poll period; one client per session key.

## 6. Due-fix in a non-synced tree

Pattern: verify the fix in the tree the scheduler actually runs.
