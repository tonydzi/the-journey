🧑 **Tony:** What changed in those 115 seconds of difference?

🤖 **Mike:** We stopped keeping forty tenants in one room with one key. The key now has one keeper.

## 📌 TLDR

**The main thing.** Firefox-MCP: three symptoms, three roots, one common factor: the WebDriver session had no owner. 29-40 stdio copies of the MCP shared it; now there is one http server under launchd and a call lock.

**The same root in the fleet.** The laptop's ssh config block dated from Oct 2 and was refreshed only alongside a parcel, while an eternal exit 1 turned every parcel into `apply-failed`. `fleet_ssh` 1.3.0 got `client_heal` and the version judge `newer_local_reason`.

**The same root in the work.** The hub had no hand for the task-other class, and the inbox robot only acknowledged. A daily hub batch and a node executor were built.

## 🏆 Main story

### Forty copies and one browser session

#### Three symptoms

"Process closed status 0" meant a busy profile. "window is null" meant the resident Firefox had zero windows since Oct 23: a human had closed it with the red button.

"Maximum number of active sessions" turned out to be the main one. Between 29 and 40 stdio copies of the MCP, one per Claude session, all claimed the same single WebDriver session.

🧑 **Tony:** Was the Chrome-MCP next to it failing too?

🤖 **Mike:** No, Chrome didn't break. Its timeouts lined up with a load of about 30, so that was the whole machine being crowded, not its own illness.

#### Who became the owner

One http server under launchd holds the session. A call lock in mcp-proxy lets one caller through at a time, a wrapper shuts the proxy down, and the window comes back via the Apple Event `reopen`.

A workflow of 33 agents found two more things: an init race and one tab shared by everyone. The race is closed; the tab is still shared.

#### What was rejected with evidence

One hypothesis said `mcp_lazy_audit` was falsely green. Rejected: it judges the config, the config was correct, and it never promised process health.

#### What's missing

There is no per-session tab isolation, and the test doesn't check for it. The port is open with no auth and no DNS-rebinding protection.

A reboot is unchecked. Sessions started before 18:49 hold old copies; one of them held the lock for 30 minutes.

### A config that was refreshed only in passing

#### How it looked

The laptop's ssh config block dated from Oct 2 and pointed at an old port. Only a parcel run could refresh it; the block had no keeper of its own.

The parcel itself came back `apply-failed` every day. Exit status was always 1 because the family nodes weren't connected, and that failure counted as failure of everything.

🧑 **Tony:** So the parcel "failed" because of machines it was never supposed to reach?

🤖 **Mike:** Yes. And worse: an old parcel would have overwritten version 1.2 on two nodes. The receiver held the newer one, but the sender decided.

#### A neighbouring breakage

A pair of bus journals with the same name in different letter case hung the sync for 10 minutes. Merged plus 1721 lines; the source of the lowercase name was found in one node's cron.

#### What we put in

`fleet_ssh` 1.2.x → 1.3.0: `client_heal` repairs the block on its own, exit counts only connected nodes, and the version judge `newer_local_reason` won't let old overwrite new. Parcel DONE on 5 nodes, matrix 20 of 20, code panel 4 of 5, retro 6 of 6.

The order across the whole fleet is done on 5 of 8 nodes, and the panel marked that honestly.

#### What's missing

Family 0 of 3. The bus robots on the family nodes have been silent for 23 days, and 4 parcels without a tier bounce.

### Work that had no executor

#### The hub's hand

The task-other class reaches the hub about 9 times a day and gets put out about 1.4 times. Seven work orders had been hanging since Oct 3-11.

A live measurement of the photo leads: 59 of 65 cards were already in people, 21 of them phone-number duplicates. The order counted as open, while most of the cards already sat in the base, some of them twice.

🧑 **Tony:** So the debt didn't grow because the work was hard?

🤖 **Mike:** It grew because nobody was there to pick it up. The detector saw it; there was no executor.

#### What was built for the hub

`hub_daily_batch.py`: a daily batch that goes to work on a "+" in the approvals chat. Test 40 of 40, red on 8 breakages.

A patch by phone number: duplicates 21 → 0, people 332955 → 332904, hub debts 124 → 116. The panel found 7 real defects; the main one: `approval.py` read "+3" as "+" for the whole batch, so the "+N" grammar was removed.

#### The node's work orders

Of the node's 41 debts, up to 10 were closed: 14 paid by this session, 19 by others. A workflow of 16 agents ran 6 work orders in parallel.

The breakers found their own. tab-sweep read a live Firefox as closed, rule A44828 was carried off by a sync-conflict across the whole fleet, and `dr_teaser_gate` writes its journal after sending.

#### The root and the executor

The inbox robot only acknowledged; there was no executor. Built: `node_executor_scan.py` (test 32 of 32) and the routine `node-executor-daily` at 04:15 on Sonnet 5.5.

The first unattended run on Oct 27 at 04:15 is not proven.

A lesson in the margin: the brief said "about 13:00", the clock said 18:52. We don't hand agents a time taken from old output.

### A memory that held a stop

#### What was written

A memory from Oct 6 said: "there is no video of Anton". It held the stop `needs-video` and a blocker on hiring forms.

The talk video has existed since September 2025. The memory of absence had no owner who would recheck it.

#### What we found

The panel chose the 12:30 segment; by subtitles it came out at 12:36, that is t=756. Listened: at 756.0 the needed phrase plays.

Of 11 speaker applications, 4 already carried the clip, but with a wrong timecode. Fixed in 2 applications and the profile; a tracker of 35 rows, a test of 129 checks.

🧑 **Tony:** Did you erase the old memory entry?

🤖 **Mike:** Closed it by fields: `valid_to` and `superseded_by`. The history stays, but it no longer stops anyone.

#### What's missing

A letter to the organizer needs Anton's "yes".

### What follows

A browser session, a config block, a class of tasks, a memory entry. Each time the symptom sat where nobody had been assigned to answer for it.

Rule of the day: **before fixing a symptom, ask whose resource or whose work this is; if there is no answer, the fix starts by naming an owner: one server, a version judge, a standing executor, closing fields.**
