Dev-log form. No canon beats for the day; assembled from session retros (6). Night tails of 10-29 included.

Defect: a status is emitted before all steps finish, or by a layer other than the one it claims to describe (wrapper vs app, shell vs child, small mode vs large mode), and the consumer reads it as the final verdict.

Position on the line. 147: verdict from one surface. 149: status from the wrong layer or the wrong moment.

## 0. Contract

Final status is written exactly once, after every step, and names the process and the mode it covers. A later "ok" must not overwrite an earlier "partial".

Wrapper exit code != app exit code. Shell exit 0 != acceptance.

Green small run proves the small run. Large mode needs its own run.

Delete only after a full-file hash match; then cleanup needs no fear. A dropped control channel (SSH) is not evidence that the job stopped.

## 7. Patterns

P1. Receipt ordering: a run emits one terminal record. Any "partial" seen earlier in the pass pins the terminal status to "partial"; a later success line may not overwrite it.

Consumers that read only the last line must be able to trust it.

P2. Exit code ownership: a wrapper (profiler, shell, broker) reports its own exit. Capture the child/app exit separately, and do not catch SystemExit without re-raising or recording its code.

P3. Multi-process codes: when child, broker and outer shell disagree (0 / 3 / 1), the run is not green. Acceptance is a review verdict, never a shell exit.

P4. Mutation sanity: before trusting a red mutant, assert that the stand loaded the mutated file (path + hash). A red run on the wrong file is a false mutation.

P5. Mode scaling: a passing small mode is evidence for that size only. Profile it, name the suspect (here file reads), then run the large mode before claiming it.

P6. Metric identity: without a session PID, physical copies and logical events cannot be separated (82 vs 41). Add the PID to the record.

P7. Fearless delete: full-file SHA256 equality before delete; keep on mismatch or missing original; verify dependent hashes after delete (177/177).

P8. Channel vs job: a dropped SSH session or a 300 s client timeout says nothing about the remote job. Check the job directly; widen the wait (1800 s) when the job is known to be long.

P9. Launch vs preparation: a prepared launch is reported as prepared. Side effects seen without a launch (SHM timestamp) are logged with "author not established".
