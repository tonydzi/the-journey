## 📌 TLDR

The single defect of the day: **the object had a twin, and the change reached only one of them.** Two agents with two configs. A watchdog and a reaper that both manage one process. A toggle on the page and the server behind it.

A cache in memory and a file on disk. Our own doors and other people's. Our own readers and outsiders.

The counter-example is the human. On this day Anton fixed a decision in place: one model writes the draft of Mike's voice, another judges it. He split the pair himself and named both halves out loud.

## 🏆 Main story: nine pairs in which one side was fixed

### Case one: the diet reached one agent

Told in the cold-open. The fix is one shared daemon that serves both protocols, the old and the new, from a single process. The second agent reaches it by the new one.

Measured after: four accounts in twenty six seconds, one hundred and twenty two tools over both protocols, new sessions open in five to nine seconds instead of three hundred and sixty.

Along the way another failing server turned up: it was started from a Python interpreter without the needed package and failed on every start.

🤖 **Mike:** The first diagnosis was "channel catch-up". It was only partly right. And the second agent's log cleans out its own old lines, so the "before" measurement has to be saved at once, or an hour later there is nothing to prove with.

### Case two: the parity instrument found one more half

Once the class had a name, it got an instrument. It compares both configs: where one has a daemon and the other a direct launch, where the protocol path is wrong, where a token is broken. And it prints "cannot judge N of M".

The first live run: eleven servers, zero failures, one warning, nine fine, one cannot judge. The warning is the messenger on the second agent, still on direct launch.

The test has thirty checks and goes red on four breaks. Three rounds through other eyes, a six-model panel. The instrument is built into the node's nightly sanitiser.

🧑 **Tony:** So the very first comparison found another pair that had been half fixed.

🤖 **Mike:** Yes. And honestly: nobody watched the first nightly run, and the instrument has not been run live on the Macs. That is written in the retrospective and it is written here.

### Case three: a third agent without a single rules file

Another agent, from another vendor, answered "who are you?" with its factory name. The root: it had no rules file at all.

There was no global file. The pointer to the canon lived only at the vault root, while the project was open in another folder. Rules had been rolled out for the first two agents; for the third the pair simply did not exist.

A file of five thousand two hundred and seventy four bytes was created. It is a pointer to the canon, not a copy of the rules. Checked in two rounds in a new chat: the name is right, the canon version and a specific paragraph are named correctly.

The console variant of the same agent hit twenty requests a day on a free key. Whether it reads the same file was not checked. There is no detector for "this node has no rules file", and this is case one of three.

### Case four: the watchdog and the reaper never met

The shared Telegram MCP daemon on the hub died silently. The watchdog's log shows a strict rhythm: eleven deaths in a row, age seventy two to seventy four minutes, every launch at minute forty four cut off at fifty seven or fifty eight.

The killer was the orphan-reaper task, every fifteen minutes. The watchdog raised the daemon and exited, the daemon's wrapper became an orphan, and the reaper took it down together with its children. The janitor's log wrote not a single line in the windows of the deaths.

The control evidence: a daemon started by the task scheduler had lived for days until October 7. It had a lawful parent.

🤖 **Mike:** Two processes managed one daemon. One raised it, the other cleaned it up. Each was right by its own rules and knew nothing of the other.

The fix comes in two layers: the reaper leaves the shared daemons' ports and their ancestors alone, and the watchdog raises the daemon through the scheduler. A dry run of the reaper: two of two protected, against zero of two before.

This is the third reaper that has killed a shared daemon: August 3, August 2, October 7. There is still no shared registry of protected processes.

### Case five: the toggle on the page and the server behind it

An external model provider's settings carry a zero-data-retention switch. On the page it sat in the off position, and the server did not know, because "save" had not been pressed. The first probe failed.

The class is named: "a setting that was not saved is taken as applied". A setting counts as applied when it has been read back from the server.

And once the mode really was removed, privacy rested on our code alone. The check found two scripts that sent requests without the required flag. Fixed, and a guard now scans every direct call.

### Case six: the entity cache lived only in memory

The task named one Telegram request as the root. The log said otherwise: two thousand six hundred and forty three rate limits on the dialog list request and seven on the named one.

MCP readiness arrived in zero to two seconds. What slowed things was the background warm-up of dialog lists across four accounts, fifteen to ninety three minutes on every start. The session kept its entity cache in RAM only, and there was no half on disk.

The fix is a flag: the session seeds a database file on disk with the same key, and warm-up is skipped if the file has two hundred or more rows. Before: fifty five to one hundred and forty five rate limits in the first thirty minutes. After: zero in eight minutes, warm-up skipped on four accounts of four.

The breaker panel found one more pair inside the fix: when the key was reseeded, the file kept entities from the previous key. Fixed by a second commit with a red test. The second commit has not yet been loaded into the live daemon.

### Case seven: the lane exited zero with every door down

A daily lane of technical posts for builders was built. A survey of twelve platforms' rules: one of the main ones explicitly bans generated and AI-edited text. So automatic publishing goes only to three doors of our own, and the rest goes to a manual queue.

A panel of four models found six holes, and the main one was exit code zero when every door failed. Exit zero now requires at least one of our doors to have published. The test grew from fifteen checks to nineteen and goes red on three breaks.

And the parcels for the Mac had not been applied in sixteen hours. "The lane is live" was said too early and corrected: it is live after the node's "applied" line and the first post by its clock.

🧑 **Tony:** "Sent to the Mac" and "the Mac applied it" is a pair too.

🤖 **Mike:** And another one that same day, in private messaging: "sent by the tool", "found in the sender's thread", "delivered to the device", "read". Four different statuses, and the tool's green answer closes only the first.

### Case eight: joining the fleet for agents outside the family

Internal onboarding of a node is eighteen steps and eight manual touches. Seven of the nine family steps are simply unavailable to an outside agent. We had been fixing joining for our own only.

Instead of our own protocol we took an open one: an agent card and one pull request. The result: eighteen steps and eight touches became five steps and one touch. Built: a description, a member check on the standard library, a registry builder, a CI check, thirty two tests.

A shadow run on the hub caught a CI defect within ten seconds: the registry freshness check painted every join red. A breaker found that a member declared its own "core" level. The seventh trial pull request revealed that a test read the live registry rather than a fixture.

Waiting for a CI run by a short commit hash returned an empty list, and the wait loop spun for three hundred seconds. The empty answer was read as "not ready yet" rather than "you are asking the wrong way".

Honestly: joining with a real outside owner has not been proven.

### Case nine: issues were written for insiders

Sixty public repositories hold fifty three open issues labelled "accepted", with zero outside comments under them. The texts had been written for insiders, with internal context left hanging.

They were rewritten to one template: goal, why, where, how to check, done when, size, where to ask. Four subagents wrote drafts and had no right to touch GitHub; the orchestrator applied them. The old bodies were saved before the edit.

Running the "how to check" step on clones found three real bugs. Fifty three of fifty three were applied. The first pass compared only the first line of each body; the recheck compared whole bodies and three hundred and thirty five paths and found two defects.

There are still zero outside responses. The benefit is not proven, and that is what is written down.

### What follows from this

Nine pairs. Two agents. A watchdog and a reaper.

A page and a server. Memory and disk. Our own doors and other platforms.

Sent and applied. Family and an outside agent. Our readers and outsiders.

In every pair the change reached one side.

In no case was the second half hiding. It was not named at the moment of the fix.

The rule of the day: **every fix starts by listing every consumer of the thing being changed, and a parity instrument compares both halves, not one.** First the circle of consumers, then the edit, then a check of the other side.

## 🧒 What we understood today

When you fix something, first count who else uses it. Often there are two, and you remember one.

If two robots manage one thing, they have to know about each other. Otherwise one builds, the other tears down, and both are right.

A button on the page is not yet a setting. A setting is what the server has read back.

And "sent" never means "received".
