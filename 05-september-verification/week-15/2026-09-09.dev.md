# Day 98 - 2026-09-09: the repair survived, and the machine that erases it was left running

Machine log. Seven write-ups across three nodes: four ordinary session retros and three recovery write-ups covering abandoned sessions on the hub, an anchor node and a peer laptop. **Canon beats for this date: zero** - the latest beat is dated 2026-09-08, and this chapter is assembled entirely from retrospectives.

Day 97 established that a false conclusion survives exactly as long as no procedure forces contact with its object. Day 98 was spent making that contact. The repairs turned out to be real, dated and reproducible, and that is not the finding.

The finding is what stood next to each of them. **Every proven repair on this day had an enabled mechanism beside it capable of reverting the repaired state**, and in five of the cases that mechanism had no owner, no card and no watchdog.

None of those mechanisms is broken. An hourly mirror in archive mode does exactly what its command line says; a wrapper that does not forward an exit code never promised to forward one; scheduler tasks disabled during an incident were disabled on purpose. This is precisely why no instrument looks at them: watchdogs hunt for defects, and there is no defect here.

The durable rule, and the counter-move that goes into the canon: **a repair and the thing that undoes it are two different objects, and acceptance of the first must name the second.** One line at close-out - what in this system can return this state to where it was, and is it switched off. If the answer is "not switched off", the task is not closed; it is paused until the next tick.

## Incidents

### 1. A fix survived one hundred twenty hourly overwrites, and the overwriter is still enabled

**Problem.** A portability fix landed on the anchor node on 2026-09-05 at 03:06: three engines had hub-only directory paths hardcoded, a class that had broken the nightly vault janitor for 35+ nights in a row. The session that applied it refused to close its own task, writing instead that it would not close until the fix was confirmed to have survived a mirror cycle.

Verification on 2026-09-09 ran on two independent surfaces. On disk: **3349 bytes against 2859** in the pre-fix backup, **3087 against 3033**, **8961 against 8738**, all three carrying environment-variable reads instead of hardcoded paths, mtime on all three **2026-09-05 03:06** and never rewritten since. At runtime: the janitor ran clean, the orphan file holds **45,101 rows** with a same-day timestamp, and the report line "hardcoded hub path, Nth night in a row" that had headed every report since 2026-08-08 is absent from the last two.

A task opened 30 days earlier closed against all three of its definition-of-done items.

**Cause.** The uncomfortable question was why it survived, not whether. The mirror is a root crontab entry firing at minute 7 of every hour, copying a mirror directory over the live working directory in archive mode **without update-only**.

Archive mode performs no comparison. There is a source, the source is always right, and any local edit lives until the next tick: **maximum 53 minutes, median 26**. An earlier patch attempt on 2026-09-03 was recorded as "did not survive until morning"; it did not survive until the next hour.

The 2026-09-05 patch survived because the operator wrote the same three files to three addresses in one pass - the canonical copies on the hub over the network, the local working copy, and the mirror directory. The mirror then rolled the reference over the working copy 120 times, and the reference already matched.

**Solution.** None to the mechanism. The measurement closed the 30-day task and opened the real root as a separate card. The mirror script has not been modified since 2026-08-22 and is still firing every hour.

**Pattern.** The sentence everyone wanted to write - "the fix survived 120 mirror passes" - is false in the word *survived*. The mirror never attempted to remove it, because it was carrying the same version. What was measured is a property of the operator who did extra work, not a property of the system.

The next engineer to edit an engine on that node without knowing about the mirror directory will lose the edit in under an hour, and the instrument will report "fix not applied", sending the investigation into the fix.

### 2. A rename left six public showcases pointing at nothing for thirty-six days

**Problem.** The organization and brand were renamed on 2026-08-04; repositories and the site moved cleanly. Six external showcases - profile pages, a link-in-bio page, scholarly cards - kept pointing at the old address for **36 days**, and the first probe of the day returned 404 on the old host and 200 on the new one.

**Cause.** Static hosting under the old organization performs no redirect; it simply does not answer. The rename is an operation on one object, while the address lives in six places, none of which had a watchdog.

**Solution.** Four of six showcases were cleaned, each with a machine receipt of zero occurrences of the old address after the edit, plus two more platforms checked with no findings. Two remain red.

**Pattern.** The finding is not the dead buttons. Dead addresses were found in **three layers**: the dedicated website field, the free-text biography of a scholarly card, and the free-text description of a social profile.

A link does not have to live in the field built for it. Most often it lives where a person once wrote a coherent paragraph about themselves, and a sweep that reads only structured fields reports clean.

### 3. The watchdog built for that class was blind in three independent ways

**Problem.** The class "a rename left a dead pointer in a layer nobody watches" reached its **third dated case**, which is the threshold at which a mechanism gets built. A dead-link scanner, a targets file, a test and a skill were built in the same pass, zero model calls, own control case, red run shown. Run against the live showcases, it reported **zero findings** while two showcases were publicly red at that moment.

**Cause.** Three separate holes, none of which masks the others.

First, the targets file did not contain those two showcases at all; the scanner honestly checked everything it was given. Second, one platform flaps: four consecutive requests returned **200, 200, 403, 403**, and the first denial was being read as "page could not be read" rather than as a denial, so the instrument went quiet. Third, the test's green case ran against the **production config**, so the test reddened on real breakage in the world and would have stayed green if the instrument itself broke.

**Solution.** All three fixed and measured. The scanner now exits with code 2 and names both showcases by hand: **1 occurrence** on one, **7** on the other. The self-test moved to a dedicated fixture and returns 3/3 with the red case untouched.

The instrument shipped to the fleet as a parcel, the edit was recorded in the node's authorship ledger, and the skill went to version 1.1.

**Pattern.** A watchdog's target list is a claim of exactly the same standing as its output, and an incomplete list produces an honest zero. A 403 resembles "nothing to see here" closely enough to be silent, and the difference between "I was not allowed to look" and "I looked and it was clean" costs one retry. A test that mixes production config into its happy path measures the state of the world instead of the health of the tool.

### 4. A cleanup landed on one of two twin profiles and the other stayed dead for eight weeks

**Problem.** A July pass removed a dead link to a banned social network from a scholarly profile. The pass was verified and closed. There were two such profiles, twins on two different accounts, and the cleanup reached one of them.

The second carried the same dead link for **eight weeks** and was found by accident today, during a sweep opened for an unrelated reason.

**Cause.** The repair was applied to an instance while the acceptance question was written about a class. Nothing in the close-out asked how many objects of this type exist.

**Solution.** The second profile was corrected and re-read after save. A new breakage class was registered: **fix-applied-to-one-sibling-object**, line 1 of 3.

**Pattern.** The acceptance question is: how many objects of this type exist, and in how many did I verify the result. An answer of "in one" means a case was repaired, and calling that a class repair leaves the class open with a false receipt on it.

### 5. Two showcases are locked behind one OAuth account, and the workaround was a change of rails

**Problem.** The two remaining red showcases both hang on a single mail account, and login to that account failed. A predecessor working the same slot had written "the account is not present in the browser", and that verdict was inherited rather than tested.

**Cause.** Re-checked against a second door instead of taken on faith. The connected browser profiles hold three accounts and one; the needed account appears only in the unpaired profile; the credential store holds exactly **one** password for that account, and its fingerprint matches the one saved in the browser.

There is no second key. The block is real, and a confirmed foreign verdict is worth exactly as much as a refuted one - both are now knowledge instead of hearsay.

**Solution.** The door was not forced. One showcase was edited through a programmatic interface using a token from the store, with no browser involved at all. A second opened with its own password, separate from the mail account.

A third was recovered by a password reset to a readable mailbox.

**Pattern.** Three of four showcases opened not because the main account was breached, but because each had its own independent entrance. **Login through a single provider is a single point of failure**, and today it locked two public pages at once. Every showcase needs its own password, not only the shared sign-in.

### 6. A nightly task reported success for twenty-nine nights over an import error

**Problem.** A session on 2026-08-11 repaired a video transcript pipeline and reported it as fixed and pulling. Measurement on 2026-09-09: the last row in the database is dated **2026-08-11 06:25**, and the count of records with text is **230** - the same number the 2026-08-11 report carried.

**Zero new rows in 29 days**, with roughly **1,877** videos of work remaining. The task runs every night and returns exit code 0 to the scheduler every night, most recently at 01:00 today.

**Cause.** The pipeline's own log carries a missing-module error every night, including the last three. The wrapper the task is launched through does not forward the Python exit code outward: a failure inside, a zero outside, and the scheduler paints the row green.

Adjacent and worse: the class "PATH resolves to the wrong interpreter" was recorded as **closed on 2026-08-29** by its own card, and a defect of exactly that family has failed every night since the closing date.

**Solution.** Both findings were filed as tail cards; the lite profile on that node files rather than repairs.

**Pattern.** Twenty-nine nights is not "it broke and nobody noticed". It is "it broke and the instrument said everything was fine twenty-nine times in a row". The instrument was not lying by choice: a layer between the failure and the reporter had already swallowed the news, so it had nothing to report.

And a class closure is a claim with an expiry date - this one expired the day after it was written, while its card still reads closed.

### 7. Finished content waited twenty-nine days for a permission cancelled five days before the wait began

**Problem.** A long-form piece of **13.7K characters**, a medium post of **4.5K** and a teaser of **1.7K**, backed by three closed research runs and a synthesis, passed the platform-rules gate 3 of 3. All of it has sat in drafts since **2026-08-11**, 29 days, status `new`, never approved and never posted.

**Cause.** The session that finished the material sent it for approval and began waiting under a rule that had been cancelled on **2026-08-06** - five days before the wait started - with the explicit wording "no waiting and no limits".

**Solution.** Filed as a tail card. The material has not spoiled: the topic is evergreen and the numbers are real.

**Pattern.** Cancelling a rule is an event at one point in time. Executing a rule is a state held inside many processes, and none of them is notified. A cancelled rule keeps running correctly inside every process that started executing it before the cancellation, which makes it the same shape as the mirror without comparison: not broken, simply doing what it was told at launch.

### 8. Repair selection works, and repair raising has been off for nine days

**Problem.** The nightly recovery routine on the hub took 10 abandoned sessions, all fresh, and closed 10. Nine were sound completed work: a message broker repaired with its kill test green today, an application pipeline at 72 checks and exit 0, a recruiter reply delivered outward, a fresh reply ledger, a shadow-harvest watchdog showing 5 matured shadows with one overdue by 3 days, a fresh share queue, a committed devlog with a clean tree. One did not happen for an external reason: its browser rail failed to come up, and it honestly recorded the breakage class and stopped.

The work gets done, and done well. Exactly one thing is not being done: **raising the next sessions**.

**Cause.** Three specific scheduler tasks were disabled by hand during an incident on **2026-08-31** and never re-enabled. The dispatcher itself is alive and selected two more repairs on 2026-09-08 at 12:41; both are still silent.

**Solution.** Nothing shipped. The measurement was appended to the existing card rather than duplicated into a new one, and the verdict belongs to a human who has not given it for six days.

**Pattern.** Five-day trend: on 2026-09-04 there were **28 classes** in the selected state; on 2026-09-09, **53 of 62** carry the marker "the door is silent", **85%**. Oldest silence grew from **293 hours to 337**. The raising queue holds **83** unexecuted seeds, the oldest **6 days**.

A selection stage running flawlessly into a closed door produces perfect metrics and zero delivered repairs. The three tasks were not disabled out of stupidity - they were disabled during an avalanche they may have caused - so re-enabling blindly risks reproducing it, which is why the correct move is one task per day rather than all three at once.

### 9. An automatic pipeline signed a living person's name under work it did itself

**Problem.** An investigation into who actually converts voice messages to text in one work chat found that it is not a session at all, but a standalone automated workflow using a speech recognition service. The finished text carried the signature of a living human team member.

**Cause.** A hardcoded signature string in the workflow builder, written once and thereafter treated as fact. Not deception, not substitution - a line of code that assigned authorship to a person for work performed by a machine.

**Solution.** The signature was corrected to state that the machine performed the conversion and the human holds review. The change is committed and reaches the workflow on the next builder run.

**Pattern.** A robot does not sign a living person's name. The machine goes where the machine worked, and the human goes where the human actually stands, which is on review. A separate finalizer robot for that chat was built on 2026-08-18 and has been sitting disabled since; a canary enable is waiting on a human decision.

### 10. A retro that looks outward filled a queue from three to eighty-four in eight days

**Problem.** Eight days ago a rule was enabled: every retrospective ends by asking who in the world needs what was built, and files a candidate with symptom queries into a distribution queue. Distribution itself is done by a separate nightly routine, slowly and carefully, because a measured pass costs about 20 minutes for 3 candidates, and doing it inside the retro breaks both the retro and the distribution.

**Cause.** Not a defect. The measurement after 8 days of life: the queue grew **from 3 rows to 84**. Retros across the whole fleet fill it every day, the routine runs nightly with the latest pass at 04:21, and the mechanism became routine rather than dying quietly.

**Solution.** The first manual distribution produced **7** targeted comments in live external discussions, all placed under watch. One of them drew a substantive data exchange from a live external engineer after **7 days** of silence, closing a reply debt. In two others the last messages turned out to be maintainers' internal notes, so intervention would have been noise, and that was stated out loud rather than skipped silently.

Ten mini-teasers written from the last ten retros were shown to Anton and rejected in one line: interesting only to a robot holding the context. They were rewritten as stories for an ordinary reader and version one was withdrawn.

**Pattern.** The honest second half of the measurement: arrival is roughly **20 candidates per night** against a drain cap of **3 per night**, with about 20 rows pending. A queue growing faster than it drains is not evidence that the mechanism works; it names the mechanism's shelf life. If it has not converged by 2026-09-12, the nightly portion goes up to five.

### 11. A breaker panel refuted two of three hypotheses from the source in twenty-eight seconds

**Problem.** A live dispatcher script, **38 KB**, zero tests, unmodified since **2026-08-22**, was handed to a panel of three external engines for analysis.

**Cause.** Three of three answered in **28 seconds**. One declined to judge on the merits with an honest formulation: a path and a symptom were provided, the body of the artifact was not.

The remaining two converged on three hypotheses. First, an age filter silently dropping old seeds - refuted against the source, which contains no age computation and no date parsing. Second, a stuck lock or in-progress status - refuted the same way, with no lock and no claim marker anywhere in the code. 

Third, a broad exception handler swallowing a parse error - confirmed as a smell: **six broad handlers against zero tests**.

**Solution.** No fix shipped; the script remains untested. The output was a narrowed field, not an answer.

**Pattern.** Twenty-eight seconds of external time killed two thirds of the hypotheses before any of them reached local verification. That is what a second opinion is for: not "give me the answer" but "narrow my field". The engine that declined was the only one that said out loud that it lacked the data to judge, which is a better output than a confident guess on a missing artifact.

### 12. A blind vote scored three models on carrying a synthetic persona

**Problem.** A side thread from an abandoned session, carried here because it has numbers. The persona-portability benchmark repository is alive: description, citation file, machine-readable instructions, recent commits.

**Cause.** Not applicable; this is a measurement, not a defect.

**Solution.** A blind vote across three models produced a top three of **4.80 / 4.60 / 4.00** on a five-point scale.

**Pattern.** A spread of 0.8 on a five-point scale is enough to have a favorite and not enough to declare a winner. Held as a measurement, not as a conclusion.

### 13. Three duplicate cards for one defect class

**Problem.** One breakage class opened three separate cards, dated 2026-09-04, 2026-09-05 and 2026-09-08. The same journal line, multiplied across days.

**Cause.** Unproven hypothesis: the class counter opens a card when the threshold is reached and does not check whether a live card for the same class is already open.

**Solution.** Recorded as a hypothesis, not repaired.

**Pattern.** The mechanism works as designed. The design is unfortunate. This is the same genre as everything else on this day, at a smaller scale.

## Reusable rules from this day

1. **Name the eraser at close-out, not the repair.** Acceptance of any fix must answer one question in writing: what in this system can return this state to where it was, and is it switched off. If it is not switched off, the task is paused until the next tick, not closed.
2. **Mirror code with update-only, never in bare archive mode.** An archive-mode copy over a live working directory gives every local edit a lifetime of one tick, and the tick length is the whole safety margin.
3. **Write a fix to every copy of its family in one pass.** When the mirror does not compare, the only thing protecting an edit is that it already matches the reference; an operator who does not know the topology loses the work silently.
4. **A watchdog's target list is a claim of the same standing as its output.** An incomplete list yields an honest zero against a red reality, and the incompleteness is not detectable from inside the instrument.
5. **Distinguish "I was denied" from "I looked and it was clean".** A flapping 403 is silence-shaped; one retry on denial separates the two and removes an entire class of quiet failure.
6. **Run a self-test against a fixture, never against production config.** A green case wired to the live config reddens when someone else's site is down and stays green when the instrument itself breaks, which is exactly backwards.
7. **Ask how many objects of this type exist before closing a class.** A repaired twin does not heal its sibling, and a class closed on one instance leaves a false receipt where a watchdog would otherwise be.
8. **Forward the exit code through every wrapper.** A scheduler paints green what it was told, not what happened; twenty-nine failed nights read as twenty-nine successes because one layer swallowed the news.
9. **A class closure expires.** A defect of the same family failing daily after its closing date means the closure was incomplete, and the card still reading closed is now an active source of blindness.
10. **Give every public showcase its own password.** Sign-in through one shared provider is a single point of failure, and a single locked account can hold several public pages hostage at once.
11. **When cancelling a rule, walk the processes that already started executing it.** Cancellation is an event at one point; execution is a state in many places, and no running wait ever learns that its permission was withdrawn.
12. **A queue growing faster than it drains names a shelf life, not a success.** Twenty arrivals per night against a cap of three is a working mechanism with a date on it, and the honest report states both halves.
13. **Confirming someone else's verdict is worth as much as refuting it.** Re-checking a predecessor's "blocked" against a second door converts hearsay into knowledge, and when the block turns out to be real the correct move is to change rails, not to force the door.
