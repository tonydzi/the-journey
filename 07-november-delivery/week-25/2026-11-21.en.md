## 🎬 Cold-open

Night. The cross-node collision watchdog finishes a run with code 1.

The healer reads the watchdog's passport, looking for the line that says what code 1 means. It does not find one, and it writes: dead task.

🧑 **Tony:** Is it dead?

🤖 **Mike:** I don't know. Code 1 means two things there: "found a collision" and "Python crashed". And the line that explains this sits lower than the healer ever looks.

## 📌 TLDR

**The main thing.** In the collision watchdog, code 1 meant both a finding and a crash. The `EXIT:` line in its passport sat on line 92, and the healer read only the first 80. Now a crash returns 4, an undelivered alarm returns 3, and a crash writes nothing to the database.

**What was done.** The doorbell watchdog did not return a single zero in three weeks, because three of its four doors are grey by design; code 2 is now listed as expected in the shared list. A panel of three outside models found two holes in the fix itself, both closed, and the red was proven with four mutants.

**Around it.** Tasks killed by the Scheduler's time limit; a "dead" hook that ran about a hundred and fifty times a day; the word `failed` inside page text; a key the scrubber missed because of one letter. Each time one signal stood for two different events.

## 🏆 Main story

### Case 1. Exit 1, two meanings

#### What the healer saw

The `cross_node_collision_watch.py` watchdog checks whether two nodes write to the same thing. It found a pair: exit 1. It crashed on a Python exception: exit 1 as well.

The `selfheal.py` healer reads codes like this: it opens the script's passport and looks for an `EXIT:` line. At `selfheal.py:513` it reads the first 80 lines. The watchdog's `EXIT:` line was on line 92.

🧑 **Tony:** So the healer never knew code 1 could be normal?

🤖 **Mike:** It never knew. To the healer, any non-zero without an explanation means "dead task". For the watchdog, code 1 is sometimes just its job.

#### Separate codes

The fix is plain. A crash now returns 4. An alarm that could not be delivered returns 3.

A finding stays 1.

On a crash, collision pairs are no longer written to the database. Before, a crashed run could leave half a record behind, and the next reader saw a finding in it.

This is the third breakage of the class. The recipe "a line in the code map, code 3, code 4, a target in the test" has now been applied for the sixth time this month.

#### A watchdog that never saw a zero

Next to it stood a second watchdog of the same kind, the one watching the doors of the session alarm clock. Over November 1-21 it had 95 runs with code 2, 34 with code 3 and 0 with code 0.

A zero could never come up. Three of the four doors are grey by their very design, and the watchdog reported that honestly with code 2. The log recorded every such run as a failure.

The fix: in `_shared/expected_exit_codes.json`, code 2 is listed for this watchdog as an expected signal. Grey is now logged as grey.

🤖 **Mike:** Ninety five "failures" were ninety five truthful answers. The watchdog kept saying one thing, and for three weeks we kept hearing another.

#### Outside eyes

I gave the fix to a panel: Grok, Gemini and GLM. They found two holes in the fix itself, and both were closed before "done".

The red was proven with four mutants through `red_proof.py`: on a broken copy the tests go red, on the fixed one they go green.

#### What is still open

Code 3 at a real red door is still logged as "dead task". So the other half of the edge is alive: a real alarm can drown in the same heap where ninety five grey runs used to drown.

The night after the fixes has not happened yet, so there is no fact at the consumer.

🧑 **Tony:** So you fixed only half?

🤖 **Mike:** I separated a finding from a crash. Separating "alarm not delivered" from "task is dead" in the Scheduler's log is still ahead.

### Case 2. A dead task killed by the alarm clock

#### Exactly four hours

The nightly TX build died. The Scheduler log: event 329, code 267014, exactly 4 hours after start.

The build itself took 3.5 hours, and after it came the tail: two gates of 29.8 and 35.9 minutes, a judge, the release write. The tail did not fit into the limit, and the Scheduler took the task down by the clock.

🧑 **Tony:** Then why did it fit before?

🤖 **Mike:** Why the nightly builds of November 17-20 ran so long, I have not proven. "Cold cache" is still a hypothesis.

#### Two numbers with no shared bar

The root: the task limit and the build duration were edited separately, by different sessions. There was no shared bar, and each session saw only its own number.

The fix: `build_timeout()` in `tx_weekly_batch.py` caps the build at "limit minus tail". With a limit of 18000 seconds the build gets 11700. The task limit itself went up to 5 hours.

#### 7.9 GB for the same answer

The second task of the same night: `tx_release_gate.py` re-read 7.9 GB of jsonl every night. The release had not changed since November 16.

Now the verdict comes from a cache keyed by sha256, and the task limit went from 30 minutes to 2 hours. Test: 52 checks, 0 failures, three new cases red on the old copy.

#### The process census

The third: `proc_census.py`. The amount of work it does is tied to a folder of 25266 files, and there was no time cap.

The runs of November 18, 19 and 21 were killed at exactly 10 minutes. Meanwhile the duration floated between 87 and 352 seconds. The fix: a scandir walk and a cap of 120 seconds per phase.

🤖 **Mike:** In all three, the log said "task failed". The task was alive and working; it was simply taken down by the clock.

#### The first check

The rule this case gave every retro: the first check of a "dead task" is the exit code and the Scheduler log, `wevtutil`, events 201 and 329. The hypothesis "the robot is alive, the non-zero is normal" was refuted in five retros that day, so it cannot be trusted without a check either.

### Case 3. The living called dead

#### A witness that was working

For four nights in a row, November 18 to 21, the nightly canon watchdog shouted: "the witness hook is dead". The dispatcher log showed 149 and 153 launches of that hook.

The hook was alive. The watchdog judged by a different sign: the canon file changed, and the witness had not seen that write.

#### Writing around the door

The witness sits only on the Write and Edit tools. `MEMORY.md` was appended from the shell through `printf >>`, 6 seconds after the lock had refused the write.

`CLAUDE.md` v7.2.0 was built by a script on another node and arrived through sync. Neither of those writes went through the witness's door.

🧑 **Tony:** So "the witness is dead" meant "someone came in through the window"?

🤖 **Mike:** Yes. One signal for two events: the witness died, or the write went around it. The watchdog always picked the first.

The fix: `canon_bypass_detector.py` searches session records for who wrote the file, in a window of 60 minutes before and 5 minutes after the modification time, and names the node and the session. Whether `MEMORY.md` belongs inside the canon circle at all is Tony's call.

#### The word failed on a page

The same illness in the browser rail. The `judge_outcome` judge looked for the words `error` and `failed` across the whole tool response.

But the response of the page reading tool is the text of the page. Any page that talked about errors made a living rail "dead".

On 2594 real responses the old rule gives 40 false failures, the new one 0. The control in the other direction: 129 real "not connected" responses stayed red.

🤖 **Mike:** A word inside the data and a word from the tool itself look the same. A judge has to know where the word came from.

### Case 4. A real red the scrubber could not see

#### The release watchdog was right

Here is the other side of the edge, and the watchdog got it right. The TX release watchdog found a full length Google API key, 39 characters, in a Codex session, and kept 5 TX venues switched off.

The scrubber before it had let that key through. The key's value does not go into this chapter, only the mechanism.

#### One letter before the key

In JSON the `=` sign is escaped as `=`. So the character right before the key was the letter `d`.

The `_TB` token boundary in `tx_publish.py` counted that letter as part of a word and could not see where the key began. All 7 token kinds turned out to be blind.

🧑 **Tony:** One letter?

🤖 **Mike:** One. To the scrubber, the key simply stuck to the word next to it.

#### The fix and the cache bridge

`\uXXXX` and `%XX` sequences now count as boundaries. The `_test_tx_token_boundary.py` test: 135 checks with 72 failures before, 0 failures now.

Changing a scrubber rule breaks the cache, so a `PRIVACY_BRIDGE` went in next to it; otherwise there would be a full day of cold recomputation. The rebuild ran from 18:45 to 21:28 UTC, rc=0. Keys in the release: 2 before, 0 now.

🤖 **Mike:** Here the red signal was real, and it was held red until a proven zero. That is what an alarm with a single meaning looks like.

### Case 5. A test that pressed a live door

The text "codex-first" showed up in a live rail 001 session. The very same text sits word for word in the fixture `_test_voice001_fire_budget_dedup.py`.

The root: red was proven on old copies, `voice001_fire.py.bak-*`, which do not have the door guard yet. And `machine.env` keeps the doors switched on, so a test running on a copy fired into the live rail.

The fix: `os.environ.setdefault` sets 4 door flags to "0" in 18 tests. Launch interception: 10 attempts before, 0 now. A diff of 19 tests before and after the fix is empty.

🧑 **Tony:** So the test was also writing into our rail?

🤖 **Mike:** It was. Red on the old copy proved the test catches the breakage. What it touches outside while doing so, nobody measured.

### Case 6. The name from disk, not from the argument

The retro wiped Tony's mark in a session title five times on two nodes, from November 8 to 17. A rule in prose from November 11 did not help.

The root: `retro_plan` trusted its `--text` argument, while the live name lives on disk. Out of 25261 session files, 551 carry `titleSource: user`, meaning a human set the name.

The fix: `session_titles.live_title(sid)` reads the name from disk, and `test_retro_plan_reads_live_title_not_stale_text` holds that behaviour.

🤖 **Mike:** The same class as the whole day: a stale signal said one thing, the live source said another, and the stale one was believed.

### What follows from this

Exit 1 of the collision watchdog. Exit 2 of the doorbell watchdog. A kill by the Scheduler's limit.

"The witness is dead". The word `failed` inside page text. Each time one signal stood for two events, and the reader picked the worse one.

With the key it went the other way, and there the release watchdog held a real alarm. The only difference: that alarm had a single meaning and its own proof.

The rule of the day: **one number, one event; before you say "dead" or "green", name the other events that produce the same code, and rule them out with a live check.**
