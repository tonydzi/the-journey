### Case 1. The social door, built three times

#### Today: reread against AK-47

I reread it and found three things of my own. The Threads and Facebook queue repeated the live `social_next_pending.py` and had no consumer, so I removed it and put the shared guard `post_rules.check` into the old queue.

The test wrote into the live usage counter, which had collected 153 lines, mostly from tests. Now the test writes to a temporary file.

🧑 **Tony:** Finish all of it.

#### Two more doors next door

Finishing turned up two more places where the new door stood next to an old one. First: the door went around the shared publication registry `pub_gate`.

The registry holds the cap "our English channel no more than one post a day". The robot never saw that cap and could release a post every 2 hours. Now the door calls `can-post` before release and `posted` after, the way the X door does.

Second: a bypass through Telegram MCP. The lock `public_tg_post_gate` already existed, and I added a rule to it: a new text post to our channel is refused with a pointer to the funnel, while replies, edits, images and files pass.

🤖 **Mike:** The registry is the nastiest of the three finds. It was the one door all along, and I set a second one beside it and called mine the only one.

#### Numbers and red

#### Panel on the retro

### Case 4. Branches GitHub can clean up by itself

#### The order and the measure

The order: clean up branches and make a skill so we always clean up after ourselves. Out came the `git_trace_audit.py` instrument, the `cleanup-after-commit` skill and a red test.

The measure: 77 own non-fork repos, 88 non-main branches in 13 of them. The `sqlite-graph-memory` repo carried 34 junk branches on the very day its paper went to the journal.

#### The root in a setting

The root of the class turned out to be a setting. `delete_branch_on_merge` was off in 77 repos of 77.

It is now on in 76; the seventy seventh is archived and read-only. From here on GitHub removes a branch after merge on its own, with none of our code.

🧑 **Tony:** And the script?

🤖 **Mike:** The script stays as an instrument for old leftovers. The door that cleans branches every day was already GitHub's; it only needed opening.

#### Counter versus identity

The first cleanup rule sounded reasonable: a merged PR exists, so the branch can go. With a squash merge `ahead_by` stays above zero forever, and the rule cannot tell merged work from work pushed to the branch after the merge.

60 of 69 candidates looked like that. A panel of 6 vendors out of 6 found it, and four named it as their first finding.

A live check showed no loss this time: for all 61 branches marked `SAFE-PR-MERGED` the tip matched the PR head. The rule was still rewritten on identity: branch tip equals the merged PR head and the base equals the main branch, red test 9 cases, the old rule fails 2.

Removal on Tony's word: 70 deleted, 0 errors. The balance adds up: 70 removed, 13 with an open PR, 3 with unmerged work, 2 unverifiable, 88 in total.

Along the way: the journal submission was completed, and red CI on main was fixed, since editors look at the repo.

### Case 7. Forty eight thousand files into the vault

Raw sessions from five nodes went into the vault through their own Syncthing folders. The receivers moved into the session archive megafolder: 48,337 files, 28.0 GB, FAILED 0.

An isolated pair proved that Revert on a receive folder erases files the source no longer has, and ignoreDelete does not help. Hence the trash can and the Revert ban.

The hub waiter expected all 6 live folders to be idle with need 0 at the same time. Sessions write every minute and folders sync one at a time, so 4 hours went nowhere.

The right criterion: need 0 for each folder at least once an hour, errors 0 in every sample, and the hub's file count equal to the source's. The counts matched: 4951 and 4951, 351 and 351, 1964 and 1964, 11105 and 11105, 19792 against 19794 on the node where a session is still writing.

### Case 9. A fuse that mistook viewing for work

On a mac Codex was restarting every 30 seconds. The cause: the spend guard `fuse.py` held 6 latched trips and killed the Codex engine every time the app opened such a chat.

The fix: stop only if new work began in that family after the previous stop. Test on a copy: the old version made 6 kills in 5 idle ticks, the new one 0, and live it ran 37 seconds with no kills.

Then, as designed, the guard stopped the chat on every "continue" from Tony. Tony called that stupid, and the guard is now disabled in a way that survives a reboot.

🧑 **Tony:** And what replaces it?

🤖 **Mike:** A deep research on how others catch looping agents collected 4 legs of 6. A guard that judges by an open file confuses viewing with work.
