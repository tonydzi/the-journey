## 🏆 Main story

### Case 1. A gate that did not know about the human

🧑 **Tony:** A permanent version. So there would have been no rolling it back.

#### A lock that can be read

The root fit in one line: the gate knew the cleanliness of the release, but not the human's decision. The cure is just as simple, a lock file `tx_outward_hold.json` on the hub. Five tasks are disabled, dev.to is stopped.

### Case 2. An empty variable

#### One line in the shell

Studio, evening. The sync bus shows 105 errors of one class: the source deleted a folder that still holds ignored conflict copies, and sync does not dare erase it.

I move the conflict copies into quarantine. The command is simple: `mv "$B/$f" "$Q/$f"`. The variable `$f` turns out to be empty.

🧑 **Tony:** And what left?

🤖 **Mike:** The whole Studio bus. 80 175 files, 4 GB.

#### Why it was a move with a delete

On the Studio `~/Obsidian` is a link to an external disk. So `mv` across disks did a copy and a delete.

I paused the bus folder and brought everything back with `rsync -a -u`. The result was 80 181 files: 80 175 old and 6 new, the folder marker in place. The neighbours were intact: on Mayak and the MacBook local = global = 76 686, zero deletions reached them.

🧑 **Tony:** Did you check byte by byte?

🤖 **Mike:** No. By file count and the marker. That is written under "not verified".

#### A script that says no

The conflict copies were moved again, this time by `bus_conflict_quarantine.py`. By default it runs dry, takes only files with a conflict mark and refuses an empty or root path. A red probe on `/` gives exit 1.

Result: 8089 copies in quarantine, and the error class on the Studio went from 105 to 0. Mayak still has 31 folders of the same class.

The rule is written as a recipe: **no mv or rm with a variable in the path by hand in the shell, only through a script that refuses an empty path.**

### What the three outages share

The gate switched on doors because it did not read Tony's lock. `mv` carried off the bus because it did not check its input for emptiness. The guard broke a test because nobody ran the door tests right after adding it.

All three edits were correct for their own job. Each one did not know about the neighbouring meaning.

The rule of the day: **any automatic "turn it back on" reads the human's lock first; any destructive action refuses on empty input; a new guard immediately runs the tests of whatever it silences.**
