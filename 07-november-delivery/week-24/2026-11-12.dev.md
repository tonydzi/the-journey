# Day 162 - 2026-11-12: a cure with a knife; two of my own repairs carried a destructive step that could erase foreign work, caught by a test and a second panel, then closed by a door in code

Dev-log form. Assembled from retros (15 files); no canon beats for 12.11 (section 8). Names of contacts from the recordings review and third parties omitted.

Defect: a repair contains a destructive step (drop-then-rebuild, delete-on-heuristic) whose safety rests on a guess (age, "hung", "stale") instead of a proof that the target is empty or owned by the repair.

Position on the line: 158 count without denominator; 159 foreign bytes at home; 160 receipt before the fact; 161 verdict on one line; 162 the fix itself is the hazard.

## 1. `reindex --force` wiped a live code index

Problem: on ZBOOK, ~88k chunks -> 0 after `reindex claude-scripts --force`. Rebuild on CPU ~5 files/min, ~15 h.

Context: 0 calls to `mcp__codeindexer__*` in 14 days with the server alive. Roots: the "index first" hint lived in skill references the agent never reads; the watchdog checked the port, not search; the index was 519 commits behind.

Cause: `--force` drops the existing index before rebuilding. Also: the "hung" server was killed twice during the night while it was slowly processing a 2000-file batch without a checkpoint; liveness was read from the `jobs` percentage.

Solution: hook `codeindexer_nudge.py` refuses `reindex --force` on live projects (test 17/17, red proven). `parse_batch_files = 200` gives checkpoints. Liveness is measured by process CPU and CHUNKS in `status`. Panel 6/6 (65 s) accepted "the --force rule exists only on paper".

Open: GPU for the indexer waits for the owner's decision.

Pattern: no full rebuild over a live index; incremental reindex or rebuild into a copy.

## 2. Worktree-ban hook could delete a copy with foreign work

Problem: the ban on worktree copies relied on a shim in front of git, bypassed by windowed apps and full-path calls.

Solution path: a git hook that fires at the end of `worktree add`, installed per repository, no admin rights.

Cause (v1): the "just created" heuristic was wrong; v1 would delete an old copy holding foreign work. Caught by the session's own test before install.

Cause (v2): v2 was live on five nodes for ~25 min. The second panel (Codex, Mistral) showed it could still delete a copy holding a foreign file if the copy was born around the hook.

Solution (v3): delete only if the copy is younger than 10 min, HEAD log has at most 2 lines, and `git status --porcelain --ignored` is empty; otherwise refuse and touch nothing. Hook 13/13 on 6 nodes; installed in 17 repositories on 5 nodes.

Counts: copies MacPro192 108, Mac16 60, hub 45. ZBook audit pass 413 s against a 900 s cap. No real stuck work found on five nodes.

Pattern: a lock that deletes proves emptiness; it does not infer it from age.

## 6. Patterns

P1. A destructive step inside a repair gets a door in code before first run; a written rule is not a door.

P2. Delete only what is proven empty or proven own; never on an age or "looks hung" heuristic.

P3. Liveness of a long job is CPU plus output count, not a progress percentage; checkpoint before you can be killed.

P4. A test that goes red on the wrong deletion and a second panel from another vendor are the two catches that worked today; neither alone caught both versions.

P5. Instruments print coverage; "0" at 16% coverage is a statement about 16%.

P6. Read the channel where the tool writes its refusal; verify against the consumer.

P7. Seeds are checked against the node and the registry before work starts.

P8. A fix is fleet-done when the neighbour's consumer reads it.
