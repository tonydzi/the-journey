# Day 160 - 2026-11-10: a receipt before the fact; a queue, a forecast or a watchdog recorded an outcome at the moment of intent, and one note recorded the opposite after the fact

Defect: a record of outcome is written by the producer at enqueue / plan time. The consumer never confirms, so "done" (or "not done") reflects intent and drifts from the world.

## 1. X teaser: queued recorded as published

Problem: log line "dist teaser done"; teaser absent on X. 179 cards without publication receipt.

Cause: the status was written at enqueue. X API returns 402 credits depleted since 08.11 22:49 UTC. On 09.11, 57 consecutive runs silently returned the post to the queue.

Solution: `x_cert.py` + Windows scheduled task "X Cert" every 30 min; it reads X (the consumer) and stamps a receipt only for a post visible there. Cards without receipt stay open.

Pattern: the producer may write "queued"; only the consumer side may write "published".

## 2. ZBook index: forecast recorded as schedule

Problem: `tx_dataset.py fleet-gap` at 10.11 06:35 UTC = 5 971 files, exit 1. Forecast "~10 nights" to close.

Cause: `brain_sessions_index` ran on CPU ("dev=cpu 207026s", 57 h). The forecast was written once and not re-checked; real estimate ~30 days.

Solution: on `device=cpu` the indexer prints SKIP and does not run; the gap stays visible.

Pattern: a forecast carries the device and rate it assumed, and is invalidated when either changes.

## 3. Note says "NOT sent" after the letter went out

Problem: a note stated "NOT sent"; the letter had been sent (turing-followup-verified).

Cause: the note was frozen at task-creation time; no back-write after the event.

Neighbours: check "the number has a source" did not prove "the number is at the source" (landings-on-benchmarks). YouTube ledger empty, 0 podcasts. Submission outcome after the extension was disabled not proven (yc-memory-pipeline).

Pattern: status fields are refreshed from the consumer (sent folder, live page, ledger), not inherited from the plan.

## 4. Watchdog buried a running task four times

Problem: `selfheal.py` recorded "Claude TX Weekly Batch" dead on 01.11, 04.11, 06.11, 08.11; the task was running.

Cause: two scheduled tasks launched one wrapper; two `>>` appended to one log; the log carried exit 1; the watchdog read it as death.

Solution: duplicate task disabled; one writer per log.

Pattern: one log, one writer; a watchdog verdict names which run produced the exit code.

## 7. Patterns

P1. Producer writes "queued"; consumer-side check writes "done". No other path to "done".

P2. A forecast stores its assumptions (device, rate) and is re-evaluated against the clock.

P3. Status fields are refreshed from the consumer after the event; a frozen "not done" is as false as a premature "done".

P4. One writer per log; two schedulers on one wrapper corrupt the exit code a watchdog reads.

P5. Admission and health gates read the current sample; min() of lagging averages hides load.

P6. Shadow before battle: name targets, false positives and refusals before enabling a reaper.
