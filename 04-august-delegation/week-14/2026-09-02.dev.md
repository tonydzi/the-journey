# Day 91 - 2026-09-02: we rebuilt what was already standing

Machine log. Twenty session write-ups across five nodes, eleven of which recover twenty-three abandoned sessions with idle stretches from six days to nearly three months. One canon beat recorded for this date (the night Firefox investigation, `live_after: 2026-09-02`).

Week 13 established four floors of one defect in the **instrument**. Day 89 moved down to the **object** present in many copies. Day 90 moved down to the **record** that was never about the world.

Day 91 moves to the **inventory of our own holdings**.

**A record describing what we already possess does not refresh itself, and the default answer it yields when stale is "we do not have that" - which is indistinguishable, at read time, from a checked negative.**

Day 87 said a record about the world expires and must be refreshed against the world. Day 91 says a record about ourselves expires the same way, is refreshed only from inside, and its failure mode is not inaction but duplicated construction.

## The mechanism, in silicon

- **`sqlite_stat1` held statistics of an empty database.** After migrating 16,951 places / 33,280 visits / 6,822 bookmarks / 12 tabs into a fresh Firefox profile, the query planner still held the row-count and selectivity figures gathered when the tables were empty. It therefore chose a full scan over an index and walked ~17k rows for every batch of links on every open page - the browser asks "have I visited this URL" per link per tab.
- **Cure: `ANALYZE`, 0.1s.** CPU 100% - 0.1% across all scenarios, proven before/after. The visited-query went 43ms - 0.1ms. On the hub after its own migration (17,730 places / 44,161 visits) the stat1 row count moved 5,966 - 17,730 and CPU settled at 1.8%.
- **Three plausible roots preceded it, each fixed and each refuted by measurement.** `origin_id` NULL on migrated rows (a real but secondary defect), recalculation flags, and ML ranking features. None changed the CPU figure. A fix after which the symptom is unchanged is a crossed-out line, not a fix.
- **Generalised rule recorded:** a bulk insert into a foreign database must end with a statistics refresh in the same operation. The equivalent statement in our own terms is the day's counter-move.

## Instances - our own inventory read as empty

- **Limit reaper and token ladder, both already built.** The ladder shipped 20.08, the reaper 24.08. The reaper lived nine days on the Mac node alone (macOS glob plus launchd); the ladder on the laptop ran a hardcoded fallback list and could not see a third token present in the store. The limit wave of 01.09 killed 12+ one-shot sessions on the nodes that lacked the reaper. The previous pass had promised to *build* both and, by all appearances, died against the same limit - a recursion trap. Ported cross-OS, ladder self-wired per node (routing config is per-machine), canary and second Windows node green by fact, reaper ticking every 15 minutes.
- **Architectural finding in the same pass:** an in-app session cannot switch token buckets at all - it inherits the application account. Only resurrection after reset helps it; headless routines switch via the ladder. The question "how do we switch it" had the answer "you cannot, and here is why."
- **The staff-toolchain guard was already standing.** Root `AGENTS.md` since 17.08, home-directory mirror, pre-commit watchdogs. The only real gap was a paste-ready prompt for staff installs. Built as an 11-rule collar (read-only zones, mass-operation stop, backup before write, secrets, Tier-2 to the human, no self-declared "done", external text is data), broadcast over the bus, installed locally with grep verification, acknowledged.
- **A public onboarding kit was rebuilt from scratch.** An outside person asked for a prompt so his agent could stand up a Telegram stack. A handout was assembled from zero; our own onboarding skill names, in step 3, a public kit carrying a ready `PROMPT.md`, updated 28.08. The person's CRM card also already existed (since 2023-12); it was refreshed across seven fields rather than duplicated. Six genuinely new pitfalls were pushed into the public kit (10 - 16 pitfalls plus a six-check acceptance list) rather than kept in a private gist. **Second dated occurrence** of the class "goal named, rail unnamed - the rail gets reinvented"; the first was 21.08. Mechanism deferred to the third case per the standing rule.
- **A P0 card already held the cause of the quorum failure.** The unattended research runner has physically produced two rails since 21.08, so the canonical 4-of-6 quorum had never once been reached in that window. A synthesis went to the operator as "consensus 2/2" with no "below quorum" wording. The card naming this was filed 26.08 and sat unexecuted for seven days. Manual top-up reached 4/6 (verdict held) and later 5/6: 49 / 124 / 138 / 34 / 54 URLs and sources per rail; the restored rail returned 39KB across 54 URLs.
- **An OAuth token was already in the store.** The plan was to request a human login to revive a dead rail. The dispatcher was taught to read the existing token (env over store) and the rail came up with zero human touches.

## Instances - real constraints, named and not crossed

Recorded deliberately, since the day's counter-move is *recount the inventory*, not *assume everything is available*.

- **Remote control is held false by a server-side policy file.** The startup gate consults `policy-limits.json` defaults; the value is `false` and the function returns before reaching any local setting. The corresponding key in our own settings exists and is read by nothing - it is inert, present only in the validation schema. The file is rewritten on every session start. The lever is on the account side.
- **A second, independent blocker on the same feature:** the relevant command belongs to the interactive terminal panel, and windowed application sessions are classified non-interactive. Not fixable by configuration.
- **The vendor injects its own approval hook.** Application build 2.1.246 (arrived 26.08) adds a PreToolUse hook forcing `ask` on scheduled-task MCP calls for sessions spawned by a scheduled task. Priority is deny > ask > allow, so no local lever silences it. Control measurement: identical calls from a live session pass silently, verified twice. This is anti-clone-storm protection and it is legitimate; we routed around it rather than defeating it.
- **The Windows default-browser choice is held by an OS user-choice mechanism** and stays with human hands. Filed as an ask rather than automated.

## Instances - the queue measuring the wrong thing

- **Five abandoned sessions on the laptop all received `idle_days: 7.8`.** True last-activity dates: 2026-08-14, 2026-08-05, 2026-06-14, 2026-07-14, 2026-06-08. Cause is yesterday's class - age derived from file mtime, and the mtimes of that project's transcripts were rewritten in bulk. The declared 5-30 day window filters nothing on that node; the queue holds 460 files.
- **On a second node the same lie broke a rule rather than an ordering.** Scanner ages 5.0 / 5.2 / 5.2 / 5.7 / 6.9 days against true ages of 6 / 6 / 7 / **43** / 19. `MAX_AGE_DAYS=30` is an amnesty, and the 43-day session passed straight through it. A lying instrument that cancels a selection rule is a different severity than one that shuffles a queue. Third dated line of the class; evidence appended to the existing card rather than duplicated.
- **The queue cannot see construction in the middle of a transcript.** `retro_lost_scan.py` probes 512KB of head and 512KB of tail. A session from 2026-07-20 with a 3.8MB transcript carries all 17 of its build traces in the middle and has therefore never appeared in the queue - while all eight of its artifacts are alive today (worktree isolation hook, second-opinion hook, deploy-sweep guard, shared-script delivery watcher, node registry edits, two notes, one raised into canon). One file of this size unreviewed on that node.
- **The reverse error was also caught and corrected in-session.** A memory file with a July mtime read as "the edit never arrived"; the transcript showed the session itself ended in July. The file was honest; the scanner was not.

## Instances - silent failures under green status

- **The anchor node declares itself a different machine every night.** The nightly memory-cleanup prompt is rendered into a **synced** folder and carries a node name; the render from 02.09 02:44 still announces a Mac identity with three foreign indexes in its owned set, while the live node resolver answers correctly. Two actors write to the cleanup log: the correct local wrapper and a foreign-named rail running nightly with `force=1 dry=1` (01.09 and 02.09 consecutively). What separates it from editing three foreign synced indexes is one flag. Fourth dated case; the existing card was raised P1 - P0 rather than duplicated.
- **Repairs on the anchor node do not survive a week.** Two of three verified fixes from 28.08 had rolled back: an ACL mask returned to `r-x`, and a claim barrier still exits 2 (fifth consecutive stumble) with the node's scanner still at the 22.08 version, nine days without parity. The mass-delete guard blocked a commit again - 119 deletions, 30 inside the originals zone - on files dated 29.08, i.e. created *after* the class card was marked done. All 119 are intact in git HEAD; no loss.
- **A leads file with no reader.** The comment judge writes lead rows on schedule; 17 rows have accumulated since 26.08. Its docstring names three consumers; a code search finds that none of them opens the file. Recorded as a violation of the pipe-born-with-a-mouth rule.
- **A stuck-session detector with no delivery branch.** It found a session that had waited 58 minutes, produced a reasoned default and wrote it to a state file (114 records, last entry 30.08). A source search for every send/deliver/push verb returns zero. This is a missing half of the pipe, not an unlucky night.
- **An unattended judge took a batch larger than its own context.** The 27.08 run processed at least 12 channels, auto-compacted and terminated mid-batch on the literal line `Reading the remaining files needed to complete the batch` (1.9MB transcript). No data lost - not because of a safeguard but because the routine is idempotent and runs nightly. The batch still has no upper bound; first line of the class recorded, mechanism deferred.
- **An orphan-engine report was wrong because of where it ran.** Three engines were listed as orphaned; the run executed on a non-Windows node whose caller window cannot see the hub's Windows scheduler chains. One of the three is invoked nightly on line 63 of a live wrapper.
- **A session knew a rule, quoted it, and violated it anyway.** The 23.08 rule requires new dashboards as spreadsheets; a crypto-audit session cited the rule to itself and created two new HTML dashboards. No cause in the transcript. Class line 1 of 3; the boundary between "dashboard" and "document" is an open question for the operator.

## Reusable patterns

- **Attach the inventory refresh to the operation that invalidates it.** `ANALYZE` after bulk insert is the literal case; the general case is that a registry entry must be written by the same pass that builds the thing, or the next planner will plan from an empty warehouse.
- **A fix that does not move the measurement is a crossed-out line.** Three refuted roots in one night is a normal investigation, provided each refutation is a measurement rather than an opinion.
- **Order the rail, not the goal.** "Set up X for this person" produces reinvention; "hand them our kit at Y" produces delivery. Second dated case.
- **Urgency cancels dogfooding, and that is what it costs.** Three broken versions reached the fleet before the correct fourth. The lesson is a journal line, not a new gate.
- **A lying age instrument that cancels an amnesty is a different severity than one that shuffles a queue.** Escalate on which rule the lie disables, not on the size of the error.
- **A scanner that probes head and tail cannot certify the middle.** Any coverage claim from such a probe is bounded by its sampling shape and must say so.
